# DATABASE_DESIGN.md
## CWS Penyuluh

### 1. Tujuan Dokumen

Dokumen ini menjelaskan rancangan database untuk sistem CWS Penyuluh.

Database dirancang untuk mendukung:

- Website publik.
- Data 42 BPP Kabupaten Garut.
- Data penyuluh.
- Akun BPP.
- Admin CWS Pusat.
- Permintaan laporan.
- Upload laporan.
- Validasi laporan.
- Revisi dan versioning laporan.
- Monitoring laporan.
- Berita.
- Approval berita.
- Video YouTube.
- Video Google Drive.
- Notifikasi.
- Audit aktivitas.

Database menggunakan MySQL dan akan diimplementasikan menggunakan Laravel Migration dan Eloquent ORM.

---

# 2. Prinsip Desain Database

Database harus mengikuti prinsip berikut:

- Setiap tabel memiliki primary key.
- Relasi antar tabel menggunakan foreign key.
- Data penting tidak dihapus secara permanen jika masih memiliki riwayat.
- File laporan tidak disimpan langsung sebagai binary di database.
- Database hanya menyimpan path atau lokasi file.
- Setiap laporan terhubung dengan penyuluh.
- Setiap penyuluh terhubung dengan satu BPP aktif.
- Setiap akun BPP terhubung dengan satu BPP.
- Admin CWS tidak terhubung dengan BPP.
- Setiap revisi laporan disimpan sebagai versi baru.
- File laporan lama tidak ditimpa.
- Status menggunakan nilai yang konsisten.
- Field yang sering digunakan untuk filter harus memiliki index.

# 6. Tabel `users`

## 6.1 Fungsi

Tabel `users` menyimpan akun yang dapat login.

Hanya dua role yang tersimpan:

- admin_cws
- bpp

Penyuluh tidak memiliki akun pribadi.

## 6.2 Struktur

| Field | Type | Constraint | Keterangan |
|---|---|---|---|
| id | BIGINT UNSIGNED | PK, AUTO_INCREMENT | ID user |
| bpp_id | BIGINT UNSIGNED | FK, NULLABLE | BPP user |
| name | VARCHAR(150) | NOT NULL | Nama akun/operator |
| username | VARCHAR(100) | UNIQUE, NOT NULL | Username |
| email | VARCHAR(150) | UNIQUE, NULLABLE | Email |
| password | VARCHAR(255) | NOT NULL | Password hash |
| role | VARCHAR(30) | NOT NULL | Role |
| status | VARCHAR(20) | NOT NULL, DEFAULT active | Status akun |
| last_login_at | TIMESTAMP | NULLABLE | Login terakhir |
| remember_token | VARCHAR(100) | NULLABLE | Laravel remember token |
| created_at | TIMESTAMP | NULLABLE | Dibuat |
| updated_at | TIMESTAMP | NULLABLE | Diperbarui |

## 6.3 Foreign Key

`bpp_id` references `bpps.id`

Rule:

Jika role = `admin_cws`

maka:

`bpp_id = NULL`

Jika role = `bpp`

maka:

`bpp_id` wajib memiliki nilai.

## 6.4 Role

Nilai:

- admin_cws
- bpp

## 6.5 Status

Nilai:

- active
- inactive

## 6.6 Relasi

User:

belongsTo BPP

BPP:

hasMany Users

# 11. Tabel `reports`

## 11.1 Fungsi

Tabel `reports` menjadi data utama laporan penyuluh.

Satu record mewakili laporan satu penyuluh untuk satu permintaan laporan.

File fisik laporan tidak disimpan di tabel ini.

File disimpan pada `report_versions`.

## 11.2 Struktur

| Field | Type | Constraint | Keterangan |
|---|---|---|---|
| id | BIGINT UNSIGNED | PK | ID laporan |
| report_request_id | BIGINT UNSIGNED | FK | Permintaan laporan |
| penyuluh_id | BIGINT UNSIGNED | FK | Penyuluh |
| bpp_id | BIGINT UNSIGNED | FK | BPP |
| latest_version_id | BIGINT UNSIGNED | NULLABLE | Versi terakhir |
| status | VARCHAR(30) | DEFAULT pending | Status saat ini |
| first_submitted_at | TIMESTAMP | NULLABLE | Upload pertama |
| last_submitted_at | TIMESTAMP | NULLABLE | Upload terbaru |
| approved_at | TIMESTAMP | NULLABLE | Disetujui |
| created_at | TIMESTAMP | NULLABLE | Dibuat |
| updated_at | TIMESTAMP | NULLABLE | Diperbarui |

## 11.3 Unique Constraint

Direkomendasikan:

UNIQUE:

`report_request_id + penyuluh_id`

Artinya satu penyuluh hanya memiliki satu laporan utama untuk satu permintaan.

Revisi disimpan sebagai versi.

## 11.4 Status

- pending_validation
- approved
- revision_required
- rejected

Status `Belum Mengirim` tidak perlu disimpan dalam database.

Belum Mengirim dapat dihitung ketika tidak ada record laporan untuk kombinasi:

`report_request_id + penyuluh_id`

Ini lebih bersih daripada membuat record kosong untuk semua penyuluh.

## 11.5 Relasi

Report:

belongsTo ReportRequest

belongsTo Penyuluh

belongsTo BPP

hasMany ReportVersions

hasMany ReportValidations

# 12. Tabel `report_versions`

## 12.1 Fungsi

Menyimpan setiap versi file laporan.

Tabel ini menjadi bagian penting sistem karena masalah utama client adalah file yang tertimpa.

Setiap revisi menghasilkan record baru.

## 12.2 Struktur

| Field | Type | Constraint | Keterangan |
|---|---|---|---|
| id | BIGINT UNSIGNED | PK | ID versi |
| report_id | BIGINT UNSIGNED | FK | Laporan |
| uploaded_by | BIGINT UNSIGNED | FK | Akun BPP |
| version_number | INT UNSIGNED | NOT NULL | Versi |
| original_filename | VARCHAR(255) | NOT NULL | Nama file asli |
| stored_filename | VARCHAR(255) | NOT NULL | Nama file server |
| file_path | VARCHAR(500) | NOT NULL | Path file |
| file_extension | VARCHAR(20) | NULLABLE | Extension |
| mime_type | VARCHAR(100) | NULLABLE | MIME |
| file_size | BIGINT UNSIGNED | NULLABLE | Ukuran byte |
| notes | TEXT | NULLABLE | Keterangan upload |
| uploaded_at | TIMESTAMP | NOT NULL | Waktu upload |
| created_at | TIMESTAMP | NULLABLE | Dibuat |
| updated_at | TIMESTAMP | NULLABLE | Diperbarui |

## 12.3 Unique Constraint

`report_id + version_number`

## 12.4 Contoh

Report ID:

100

Versi:

1

File:

laporan_rafi_v1.pdf

Kemudian revisi:

Report ID:

100

Versi:

2

File:

laporan_rafi_v2.pdf

File versi pertama tetap ada.

# 14. Alur Penyimpanan Laporan

Admin membuat:

`report_requests`

BPP upload pertama.

Sistem membuat:

`reports`

Kemudian:

`report_versions`

Status report:

pending_validation

Admin validasi.

Sistem membuat:

`report_validations`

Jika revisi:

BPP upload lagi.

Sistem tidak membuat `reports` baru.

Sistem membuat:

`report_versions` versi berikutnya.

# 28. Delete Strategy

Data penting sebaiknya tidak menggunakan hard delete.

Gunakan status atau Soft Deletes pada data tertentu.

Soft Deletes direkomendasikan untuk:

- users
- bpps
- penyuluhs
- report_requests
- news
- videos

Tambahkan:

`deleted_at`

File laporan dan riwayat validasi sebaiknya tidak dapat dihapus sembarangan.

Untuk laporan yang salah, lebih aman menggunakan status daripada hard delete.

# 29. Cascade Rules

Gunakan cascade dengan hati-hati.

Contoh:

Jika News dihapus:

News Media dapat menggunakan cascade delete.

Namun jika BPP dinonaktifkan:

Jangan hapus penyuluh.

Jangan hapus akun.

Jangan hapus laporan.

Ubah status BPP menjadi inactive.

Jika penyuluh sudah memiliki laporan:

Jangan hard delete penyuluh.

Gunakan status inactive.

# 35. Query Monitoring Belum Mengirim

# 53. Business Rules Database

DB-BR-01

Satu akun BPP hanya terhubung dengan satu BPP.


DB-BR-02

Satu BPP dapat memiliki lebih dari satu akun.


DB-BR-03

Admin CWS tidak memiliki `bpp_id`.


DB-BR-04

Setiap penyuluh terhubung dengan satu BPP.


DB-BR-05

Satu penyuluh hanya memiliki satu laporan utama untuk satu permintaan laporan.


DB-BR-06

Setiap revisi menghasilkan record baru pada `report_versions`.


DB-BR-07

File versi lama tidak boleh ditimpa.


DB-BR-08

Setiap proses validasi harus terhubung dengan versi laporan.


DB-BR-09

Hanya Admin CWS yang dapat melakukan validasi.


DB-BR-10

Berita BPP harus melalui approval sebelum publish.


DB-BR-11

Video Google Drive hanya menyimpan link, bukan file video.


DB-BR-12

Data historis tidak boleh hilang hanya karena akun, BPP, atau penyuluh dinonaktifkan.
